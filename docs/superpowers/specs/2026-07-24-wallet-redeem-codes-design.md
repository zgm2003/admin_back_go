# 钱包兑换码充值设计

**日期：** 2026-07-24
**状态：** 已确认
**前置关系：** 本设计先于 `2026-07-24-ai-chat-consumer-pricing-wallet-design.md` 实施；本期继续使用现有 cents 钱包，后续由 AI 计费项目统一迁移到 money units。

## 1. 目的

在不依赖支付宝等支付网关完整联调的情况下，为平台提供一条可审计、不会重复入账的余额发放路径：管理员在支付管理下批量生成固定人民币面额的一次性兑换码，登录用户在“我的钱包”兑换，金额原子进入现有钱包并显示在资金明细中。

兑换码是独立资金来源，不伪装成支付订单，不创建支付回调事实，也不建立第二套余额体系。

## 2. 已确认规则

1. 第一版只支持人民币余额兑换码，不支持订阅、并发额度、优惠券或随机面额。
2. 每个生成批次使用同一固定面额，管理员填写数量、可选过期时间和备注。
3. 过期时间留空表示永久有效；到期后不可兑换，但记录继续保留。
4. 未使用兑换码可由管理员作废；已使用兑换码不可修改、作废、删除或再次启用。
5. 码值只能由服务端安全随机生成，管理员不能手工指定。
6. 兑换码以明文持久化；具有后台查看权限的管理员可以查看、复制和导出完整码值。
7. 管理页面及操作权限明确授予当前内置管理员角色，其他角色不自动授权。
8. 同一码最多给一个用户入账一次。在请求尚未被失败限流阻断时，同一用户重复提交自己已经兑换的码，幂等返回首次兑换事实；其他用户只能得到通用不可用错误。
9. 兑换成功同时增加当前余额和累计充值，资金明细来源为独立的 `redeem_code`，显示“兑换码充值”。
10. 用户兑换失败按登录用户跨实例限流：10 分钟内最多 10 次失败；成功和本人幂等重放不计为失败。
11. 限流依赖不可用时兑换入口 fail closed，不能绕过保护继续试码。
12. 本期兑换码面额最多两位小数并保存为 cents；禁止为了未来 money units 提前双写两套金额。

## 3. 当前项目事实

- 钱包由 `internal/module/payment/wallet` 拥有，当前使用 `balance_cents`、`total_recharge_cents` 和 `total_consume_cents`。
- `wallet_transactions` 已使用 `(source_type, source_id)` 唯一身份保证资金变动幂等。
- 当前通用 `wallet.Credit` 只接受 AI 退款，并且不会增加累计充值，不能直接拿来完成兑换码充值。
- 支付充值通过 `payment_recharges`、支付订单和回调 finalizer 入账；兑换码没有外部支付事实，不能伪造该链路。
- 当前用户自助钱包接口使用 `Authenticated()`，管理端钱包与收支明细使用 RBAC 权限。
- “我的钱包”已有余额概览、充值入口和资金明细；后台“支付管理”已有支付配置、收支明细、用户钱包和充值收银台。
- RBAC 没有隐藏的超级管理员绕过。当前发布契约将 `roles.id=1` 作为内置管理员角色身份，显示名称不是稳定授权依据。
- Redis 已是跨实例能力依赖，可以承载兑换失败计数，但不能成为钱包正确性的唯一事实源。

## 4. 范围

### 4.1 本期包含

- 后台固定面额批量生成兑换码；
- 明文码查看、复制、筛选和 CSV 导出；
- 未使用码的单个或批量作废；
- 用户在“我的钱包”提交兑换码；
- 原子兑换、钱包入账、累计充值与资金明细；
- 本人幂等重放与并发唯一赢家；
- 按用户的跨实例失败限流；
- 支付管理菜单、RBAC 权限、内置管理员授权；
- Admin Contract Bundle、前端生成客户端、i18n 与针对性短测试。

### 4.2 本期不包含

- 管理员手工指定或编辑码值；
- 一个批次包含多个面额或随机面额；
- 多次使用、部分使用、余额扣减码或退款码；
- 订阅、会员、并发额度、优惠券、邀请奖励和促销规则；
- 用户兑换历史独立页面；资金明细已经是权威历史；
- 支付订单、支付渠道、支付回调或外部对账；
- 邮件、短信自动分发兑换码；
- 对兑换码进行加密或只保存摘要；
- 物理删除兑换码、批次或对应钱包流水；
- 新增密钥或本需求专用环境变量；
- 本期提前迁移钱包到 money units。

## 5. 选定架构

### 5.1 独立兑换码能力，复用钱包资金能力

在 payment capability 内新增边界清晰的 `redeemcode` 子模块：

- `redeemcode` 拥有批次、码值、生成、过期判断、作废、兑换编排与管理查询；
- `wallet` 继续唯一拥有余额、累计充值、资金流水、行锁和金额守恒；
- Admin transport 负责后台管理和当前用户自助兑换的协议映射，不直接访问数据库或 Redis；
- Redis adapter 只提供失败限流，不参与资金提交。
- 完整码 CSV 是有界、同步、仅响应内存在的敏感数据导出：复用 `internal/module/export` 的通用 CSV writer，但不创建 `export_tasks`，也不把明文码上传 COS 或通过通知分发长期下载链接。

调用关系保持：

```text
route -> handler -> service -> repository -> model
```

兑换 service 使用共享 MySQL 事务调用 wallet 提供的窄事务参与接口。`redeemcode` repository 不能直接更新 `user_wallets` 或插入 `wallet_transactions`，wallet 也不负责生成、过期或作废兑换码。

### 5.2 不采用的方案

1. **把兑换码伪装成充值订单：** 会产生没有支付渠道、支付订单和回调的假充值，污染支付对账。
2. **把全部兑换码逻辑塞进 wallet：** 会让钱包承担凭证生成、过期、导出和限流，破坏模块职责。
3. **先标记兑换码已用，再 best-effort 入账：** 会产生“码已失效但余额没到账”的资金事故。
4. **使用 Redis 锁保证唯一兑换：** Redis 只能辅助限流；资金唯一性必须由 MySQL 行锁、事务和唯一约束保证。
5. **为未来精度同时写 cents 与 units：** 会形成两套可写资金事实，本期禁止。

## 6. 数据模型

### 6.1 `redeem_code_batches`

批次保存：

- `id`；
- 唯一 `batch_no`；
- 管理员客户端 `request_id` 与请求指纹；
- `request_fingerprint_version=redeem_batch_request_v1`；
- `amount_cents`，正整数；
- `quantity`；
- 可空 `expires_at`；
- `note`；
- `created_by`；
- `created_at`、`updated_at`。

批次和兑换码主键统一使用有符号 `BIGINT`，与 Go `int64` 以及 `wallet_transactions.source_id` 的现有类型保持一致；`created_by`、`used_by` 继续匹配 `users.id` 的 `INT UNSIGNED`。

约束：

- `(created_by, request_id)` 唯一；
- `amount_cents` 范围为 `1` 至 `100_000_000`，即 `¥0.01` 至 `¥1,000,000.00`；
- `quantity` 范围为 `1` 至 `1000`；
- 非空 `expires_at` 必须晚于服务端创建时间；
- 金额、数量、过期时间和备注在批次创建后不可修改；
- `quantity` 必须始终等于该批次实际兑换码行数；
- 批次不删除，状态统计从兑换码派生。

管理端批量生成必须携带 `^[A-Za-z0-9][A-Za-z0-9._:-]{0,127}$` 的 ASCII `request_id`。过期时间先转 UTC 并截断到数据库 `DATETIME(6)` 的微秒精度；备注去除首尾空白、拒绝控制字符并按数据库字符语义限制为最多 255 个字符。请求指纹使用版本化 canonical JSON，覆盖 `amount_cents`、数量、规范 UTC 过期时间或 `null` 以及规范备注，再计算 SHA-256。重放必须同时校验指纹版本和摘要：相同 ID、相同版本/指纹返回原批次与原码值；相同 ID、不同版本或指纹返回冲突，避免响应丢失后重复发行一批余额凭证。`expires_at > created_at` 只约束首次创建；重放必须先识别既有 request identity，因此即使重试发生在原批次过期以后，也仍返回原批次，不能按当前时间把它误判为一次新的非法创建。

### 6.2 `redeem_codes`

每个兑换码保存：

- `id`；
- `batch_id`；
- 唯一规范明文 `code`；
- `state`：`unused`、`used` 或 `voided`；
- 可空 `used_by`、`used_at`；
- `created_at`、`updated_at`。

批次是面额、过期时间与备注的唯一来源，兑换码不复制第二份可修改金额。外键禁止级联删除批次、用户或钱包事实。

业务状态固定为：

```text
unused -> used
unused -> voided
```

`expired` 是查询投影，不是第四个持久化状态：

```text
state = unused AND expires_at IS NOT NULL AND expires_at <= server_now
```

过期码仍可由管理员作废，以形成明确管理事实；它不能兑换。`used` 和 `voided` 都是不可逆终态。本期没有删除接口，也不使用后台任务批量改写过期状态。

### 6.3 钱包来源

钱包新增来源：

```text
source_type = redeem_code
source_id   = redeem_codes.id
direction   = in
```

现有 `(source_type, source_id)` 唯一约束保证一个码最多产生一条入账流水。该来源流水必须始终保持 `is_del=2`；若发现同来源软删除流水，属于完整性事故，不能把它当成无流水后再次入账。资金明细与字典新增“兑换码充值”，remark 只记录批次号等非秘密信息，不能包含完整码值。

wallet 新增专用事务参与能力，用于在既有事务内同时：

- 按 `user_id` 锁定当前 active 钱包，确实不存在时创建；若唯一身份已对应软删除钱包则报告完整性错误，不能创建第二个钱包事实；
- 检查 `balance_cents + amount_cents` 与 `total_recharge_cents + amount_cents` 不溢出 `int64`；
- 增加 `balance_cents`；
- 增加 `total_recharge_cents`；
- 写入唯一钱包收入流水。

该能力不经过支付充值 finalizer，也不能开放成管理员任意加余额接口。

## 7. 码值规则

展示格式固定为：

```text
ZHR-XXXX-XXXX-XXXX-XXXX-XXXX
```

- 随机部分包含 20 个字符；
- 使用 `crypto/rand`，禁止时间戳、自增 ID、普通伪随机数或可预测摘要；31 字符 alphabet 必须用拒绝采样消除取模偏差（字节值仅接受 `< 248` 后再 `% 31`），不能直接对任意随机字节取模；
- 字符集排除 `0/O/1/I/L` 等易混字符，约提供 99 bit 随机空间；
- 数据库使用 ASCII 二进制比较的唯一索引，不能依赖语言相关或大小写模糊 collation；
- 单码拒绝采样与批内去重都必须有固定尝试预算；异常 reader 持续给出被拒字节或重复码时返回受控错误，不能无限循环；
- 单次生成先保证内存内无重复，再依赖数据库唯一约束兜底；极小概率碰撞时重新生成，超过受控重试次数则整批回滚。

服务端接收用户输入时：

1. 将原始输入限制为最多 128 bytes 并拒绝控制字符；
2. 去除首尾空白；
3. 只容忍 ASCII 空格和 `-` 分隔符；
4. 转为 ASCII 大写并重新构造规范格式；
5. 校验 `ZHR` 前缀和随机字符集。

Unicode 同形字符、额外前后缀和非法字符均拒绝。后台创建、查询和导出始终使用数据库中的规范格式。

## 8. 批量生成与作废

### 8.1 生成

生成请求包含：

```json
{
  "request_id": "admin-client-request-id",
  "amount": "50.00",
  "quantity": 100,
  "expires_at": "2026-12-31T15:59:59+08:00",
  "note": "活动发放"
}
```

金额只接受匹配 `^(0|[1-9][0-9]*)(\.[0-9]{1,2})?$` 的 ASCII 十进制字符串，不接受正负号、指数、千分位、首尾空白、前导零或省略整数部分；按整数位/小数位拆分并在边界检查后得到 cents。禁止 `float32`、`float64`、`ParseFloat` 或 JSON number。`expires_at` 为空表示永久有效，持久化时统一为 UTC。

service 规范化请求并计算指纹后，先按 `(created_by, request_id)` 查询既有批次：同版本/指纹立即返回原批次与原码，不依赖随机源，也不执行仅针对首次创建的未来过期校验；不同版本/指纹返回冲突。普通查询未发现记录时生成候选码并进入 `CreateOrReplayBatch`，但 service 仍不能仅因当前时间已过期就提前返回，因为还可能存在尚未可见的并发 request race；repository 必须在事务锁/唯一键 race 后再次回读并执行相同比对，只有最终确认要首次插入时才校验未来过期时间。批次和全部码在同一事务中创建，任何校验、随机源、唯一约束或插入失败都不能留下部分码。成功响应返回批次与全部完整码；之后拥有列表权限的管理员仍可查看或导出明文码。

### 8.2 作废

管理员通过同一批量状态接口提交 1 至 1000 个、去重后的正整数 ID。事务锁定全部目标码并按稳定顺序处理：

- `unused`，包括已经过期的 unused：转为 `voided`；
- 已经 `voided`：作为幂等成功；
- 任一 `used` 或不存在目标：整批冲突，全部不变；本期没有租户/创建人级资源范围，不能虚构按批次创建人限制的第二套授权。

作废与用户兑换并发时，数据库行锁后的第一个合法终态转换获胜。不存在“作废后仍入账”或“入账后又作废”。

## 9. 用户兑换事务

用户提交规范化码值后，service 在一个短 MySQL 事务内：

1. 按码值查询并 `FOR UPDATE` 锁定兑换码；
2. 读取不可变批次面额和过期时间；
3. 若状态为 `used` 且 `used_by` 是当前用户，读取原钱包流水，并验证流水处于 active、用户、钱包归属、方向、来源、金额以及 `balance_before + amount = balance_after` 与批次完全一致后幂等返回；当前钱包余额允许已经被后续流水改变，不能错误要求它仍等于该历史流水的 `balance_after`；任一必要事实缺失、不一致或同来源流水已被软删除都返回平台完整性错误并告警，不能盲目补写或返回成功；
4. 若不存在、格式无效、已过期、已作废或已被其他用户使用，返回统一不可用结果；
5. 对合法 `unused` 码，通过 wallet 事务参与接口锁定钱包并按 `(redeem_code, code_id)` 创建收入流水；若该来源已经存在流水，视为数据完整性错误并全部回滚，不能把未用码静默修复成已使用；
6. 将码从 `unused` 原子转为 `used`，保存 `used_by` 与 `used_at`；
7. 提交后返回本次金额、原钱包流水和最新钱包概览。

`used` 且属于本人的幂等判断先于过期判断。对仍为 `unused` 的码，过期判定时刻必须在成功取得兑换码 `FOR UPDATE` 行锁之后读取，并与本次 `used_at` 使用同一个 UTC 微秒时刻；禁止使用进入 service 或等待行锁前捕获的旧 `now`，否则临近过期请求可能在实际取得锁后仍被错误放行。

锁顺序固定为“兑换码行 -> 钱包行”。作废也先锁兑换码，所有实现遵循同一顺序以降低死锁风险。事务发生死锁时只重试本地事务，不重新生成码或创建不同资金身份。

以下事实必须同成同败：

```text
兑换码 used
+ 钱包余额增加
+ 累计充值增加
+ 唯一资金流水
```

数据库异常、溢出或钱包写入失败时全部回滚，兑换码仍可重试。钱包加法溢出以及既有兑换/流水事实不一致统一映射为 `wallet.redeem.integrity_violation`，属于平台完整性失败，不计入用户试码失败；数据库连接、超时等临时故障映射为 `wallet.redeem.dependency_unavailable`。Redis 不参与该事务，Redis 故障不能造成半入账。

## 10. 失败限流

限流身份固定为当前认证平台与用户 ID，不接受前端 user ID。策略固定为：

```text
10 分钟内最多 10 次用户原因导致的失败
```

计为失败：格式非法、码不存在、过期、作废或已被其他用户使用。不计为失败：成功、本人幂等重放、数据库/Redis 等平台依赖故障。

Redis adapter 使用原子脚本维护固定窗口失败数和 TTL，并使用 `SET NX PX`、随机 128-bit owner 与 compare-and-delete Lua 的短时用户级尝试锁串行化同一用户的兑换判断。这里不复用带持久 fencing counter 的 `internal/infra/redislock`：试码锁不保护资金正确性，不需要 fencing token，而为每个用户留下永久 `:fencing-token` key 会形成无界 Redis 状态。尝试锁 TTL 固定为 15 秒；成功取得锁后立即启动总 attempt timeout，它必须覆盖失败状态读取、规范化和 MySQL 事务并固定小于锁 TTL，不能到访问数据库前才开始计时。key 使用项目既有命名空间、平台和用户 ID，不包含兑换码。尝试 key 最迟随 TTL 消失，失败 key 最迟随 10 分钟窗口消失，不得留下第三个永久 key。Redis 锁只收紧试码行为，兑换唯一性仍由 MySQL 保证。

处理顺序为：

1. 取得用户尝试锁；失败则返回可重试限流结果；
2. 原子读取失败数，达到 10 次时返回 HTTP 429 与 `Retry-After`；
3. 执行规范化与兑换事务；
4. 用户原因失败时原子增加失败数，首次失败设置 10 分钟 TTL；
5. 成功、本人幂等重放或平台故障不增加失败数；
6. 按 owner 释放尝试锁。

第 10 次实际用户失败仍返回该次通用不可用结果并把计数写为 10；从下一次请求起在访问 MySQL 前返回 429，直到固定窗口到期。阈值已达时限流优先于业务幂等，包含本人重放在内的所有新提交都返回 429；“本人重放不计失败”只表示获准执行的重放不会增加计数或清空既有计数，不能成为绕过限流的数据库探测通道。transport 在 JSON 绑定前设置有界 request body；可解析 JSON 中的空 code、超过 128 bytes 或格式非法 code 由 service 在锁内分类并计数，无法解析为请求 DTO 的畸形 JSON 或超过 transport body 上限的请求直接拒绝且不算一次试码。

Redis 客户端、脚本或计数读写不可用时返回 HTTP 503，禁止回退成不限流数据库查询。用户原因一旦已由 MySQL 分类，即使客户端随后取消 HTTP 请求，也必须使用 `context.WithoutCancel` 派生的短超时清理上下文写入失败计数；释放尝试锁同样使用该清理上下文，防止通过主动断连逃避计数。成功不会清空用户此前真实失败次数，只是不新增失败。repository 一旦返回新兑换成功或已验证的本人幂等重放，随后释放尝试锁失败只记录受控告警并依赖锁 TTL 回收，仍返回成功，不能把已经到账的事实伪装成业务失败。

## 11. HTTP 与权限契约

### 11.1 管理端

在 `/api/admin/v1/payment` 下使用资源式接口：

- `GET /redeem-codes/page-init`：筛选字典；
- `GET /redeem-codes`：码列表；
- `POST /redeem-code-lookups`：按请求体中的完整码精确查询；
- `POST /redeem-code-exports`：按请求体中的当前筛选条件生成有界 CSV；
- `POST /redeem-code-batches`：批量生成；
- `PATCH /redeem-codes`：将一组码幂等作废。

不新增 `/generate`、`/void` 等 POST 动作别名。普通 GET 列表支持批次号、持久化/派生状态、兑换用户、备注和时间范围筛选，默认按 ID 倒序，但不接受完整码或码值片段。完整码精确查询只由 `POST /redeem-code-lookups` 接受请求体 `{"code":"..."}`，按第 7 节规则规范化后返回唯一记录或空结果，不提供模糊匹配，避免秘密进入 URL、访问日志或浏览器历史。CSV export body 复用同一组非码值筛选字段但忽略分页，repository 固定只读取 `MaxExportRows + 1` 行；本期 `MaxExportRows=10000`，超过时拒绝并要求管理员缩小筛选范围，不能把全表无界加载进 Go heap。lookup 与 export 都使用 list 权限，并与所有包含完整码的响应一样发送 `Cache-Control: no-store`。

权限固定为：

| 权限 | 用途 |
| --- | --- |
| `payment_redeem_code_list` | 打开页面、查看完整码、筛选和导出 |
| `payment_redeem_code_generate` | 批量生成 |
| `payment_redeem_code_void` | 作废未使用码 |

菜单“兑换码管理”挂在“支付管理”下。读取完整码和导出都要求 list 权限；生成和作废不能只依赖前端按钮隐藏。

### 11.2 当前用户自助兑换

```text
POST /api/admin/v1/wallet/redemptions
```

该接口创建一次钱包兑换事实，使用 `Authenticated()` 并从认证身份取得用户 ID，不要求后台兑换码 RBAC 权限，不提供 `/wallet/redeem` 兼容动作别名。

请求只包含 `code`。成功响应包含规范金额字符串、原钱包流水身份/余额快照和最新钱包概览，不返回批次备注、创建管理员或其他用户信息。

### 11.3 用户兑换稳定错误

| `error.code` | HTTP | retryable | 含义 |
| --- | ---: | --- | --- |
| `wallet.redeem.code_required` | 400 | false | 输入为空 |
| `wallet.redeem.unavailable` | 400 | false | 格式非法或兑换码不可用 |
| `wallet.redeem.rate_limited` | 429 | true | 失败次数已达上限或同用户请求正在处理 |
| `wallet.redeem.rate_limit_unavailable` | 503 | true | 限流依赖不可用 |
| `wallet.redeem.dependency_unavailable` | 503 | true | 数据库等依赖暂时不可用 |
| `wallet.redeem.integrity_violation` | 500 | false | 钱包金额溢出或既有兑换/流水事实不一致 |

这六个值是响应 `error.code` 的稳定机器码，不只是 i18n `MessageID`；实现可使用同名 MessageID，但必须显式构造对应的 code/category/retryable。它们专属于 `POST /wallet/redemptions`；后台生成、查询、导出和作废使用各自 module-scoped 的管理错误，不能被强行压成这六类。除本人幂等成功外，普通用户不能从状态码、错误码或文案区分未知、过期、作废和他人已使用。后台接口可以按权限返回明确管理冲突。

## 12. 前端交互

### 12.1 兑换码管理

支付管理下新增“兑换码管理”页面：

- 顶部使用现有紧凑搜索与表格模式，不做营销式大卡片；
- “批量生成”打开表单，字段为面额、数量、可选过期时间、备注；
- 生成成功后展示本批完整码并提供复制与按 `batch_no` 筛选的 CSV 导出；
- 列表展示完整码、批次、面额、状态、过期时间、兑换用户/时间和创建信息；
- 只对未使用/已过期码显示作废操作；已使用码只读并可定位对应资金流水；
- 批量作废使用现有确认组件，明确显示选中数量。

CSV 复用 `internal/module/export` 的通用 writer，输出 UTF-8 BOM、正确字段引用，并中和备注、账号等首个非空白字符为 `= + - @` 的电子表格公式内容。前端只把响应中的有界文本交给临时 Blob，下载后释放 Blob URL；服务端不把完整码 CSV 保存为 export task/COS 对象，导出内容和前端错误日志也不得上传到遥测服务。

包含完整码的管理列表、生成结果和导出响应必须发送 `Cache-Control: no-store`；码值只能放在请求体或响应体，不得进入 URL path/query、页面标题、浏览器持久化 store、localStorage 或 sessionStorage。前端路由跳转和刷新不能把完整码重新拼入地址栏。

### 12.2 我的钱包

在现有“充值”按钮旁增加带票券图标的“兑换码”次按钮。点击后打开紧凑弹窗：

- 单个兑换码输入框；
- 提交期间禁用重复点击；
- 成功后关闭弹窗，显示到账金额，并刷新钱包概览和资金明细；
- 兑换响应已经确认成功时，以响应钱包为即时事实；后续概览或明细刷新失败只能提示部分信息刷新失败，不能把已到账表现成兑换失败或自动重提；
- 通用不可用错误不暴露码的具体状态；
- HTTP 429 显示稍后再试，HTTP 503 显示服务暂不可用。

不新增用户兑换历史 Tab。资金明细的来源筛选增加 `redeem_code`，收入行显示“兑换码充值”。

## 13. 明文安全与审计

用户已确认不加密兑换码，安全边界固定为 RBAC、传输保护和泄露面控制：

- 数据库和授权后台可保存/读取完整码；浏览器 transport 继续使用 TLS；
- 普通用户接口永不返回未兑换码、他人码或批次列表；
- 日志、指标、trace、错误响应和操作审计禁止记录完整码；
- 数据库唯一约束错误必须映射为受控错误，不能把含完整码的驱动原始错误直接写入日志或响应；
- 需要关联时只记录兑换码 ID、批次 ID，不记录完整码或其摘要；
- 后台生成、导出和作废操作审计，但审计 payload 不保存完整码或完整 CSV。当前 operation-log middleware 会在 handler 校验前读取原始请求体，因此 export、generate、void 和用户兑换均必须 `SkipRequestPayload`，只保留操作者、会话、平台、路由、动作、状态和延迟等受控审计元数据；generate、void 和用户兑换使用 required audit，导出使用同时跳过请求/响应 payload 的普通审计。generate 还必须跳过包含完整码的响应，用户兑换跳过请求和响应；导出不能使用 required-audit writer，因为该 writer 即使跳过响应 payload 仍会暂存完整响应并在 1 MiB 时失败，不能让合法的有界 CSV 被中间件改写成 500；
- 指标标签禁止 user ID、code、batch number 等高基数身份；
- 管理员复制和导出权限不会自动扩散给其他角色。

本需求不读取或修改 `APP_SECRET`、`APP_SECRET_PREVIOUS`，也不新增兑换码密钥。

## 14. 权限挂载与发布

版本化迁移和 seed 同步新增菜单/按钮权限。MySQL 建表 DDL 与权限/角色 DML 必须拆成前后两个迁移版本：前一个只创建兑换码事实表，后一个只做可回滚、可重试的授权事务；禁止在同一 Atlas revision 中先隐式提交 DDL、再执行可能失败的权限 DML。当前发布基线以 `roles.id=1` 作为内置管理员角色稳定身份，因此权限迁移必须：

1. 校验 `roles.id=1 AND is_del=2` 唯一存在；`roles` 表没有 `status` 字段，不虚构“角色启用”条件；
2. 校验支付管理父权限唯一存在；
3. 创建或恢复兑换码 PAGE/BUTTON 权限；
4. 向 role ID 1 幂等授予 `payment`、`payment_redeem_code_list`、`payment_redeem_code_generate`、`payment_redeem_code_void`；
5. 在同一迁移事务内补齐所有满足 `users.role_id=1 AND status=1 AND is_del=2` 的 active Admin 用户缺失的 `authz_principal_versions(platform=admin)` 行，再统一递增版本；该数据库更新本身不宣称已刷新 Redis；
6. 校验授权恰好存在且有效；
7. 不按“管理员”显示名称猜角色，不向其他角色批量授权。

任一前置条件不满足时迁移失败，不能静默跳过。reconciliation 还必须双向验证：每个批次的 `quantity` 等于实际码数；每个 used 码恰有一条 `is_del=2`、同用户、同金额、同钱包归属且算术成立的 `redeem_code` 收入流水；每条 `source_type=redeem_code` 流水都必须为 active 并反向对应一个 used 码；unused/voided 码没有对应流水。新增路由进入 route metadata，并从编译路由重新生成 Admin Contract Bundle 与前端客户端。

在线权限变更继续使用既有 `PrincipalService.Mutate` 的 `Begin -> 数据库事务/版本递增 -> Publish` 协调，不允许业务代码绕过它直接改授权。版本化迁移无法参与 Redis `Begin/Publish`，因此发布依赖现有 Admin 后端启动门槛：每个新实例在接收流量前调用 `PrincipalService.Reconcile`，把 MySQL 中的当前 principal version/role 发布到 Redis、删除旧版本 route-access snapshot；reconcile 失败则实例启动失败。只有所有新实例通过该门槛并且旧实例退出流量后，权限发布才算完成。

发布顺序：

1. 从编译路由生成并校验 Admin Contract Bundle 与前端客户端，把验证过的后端和前端产物固定为同一发布版本；
2. 进入受控 Admin 发布窗口并暂停流量，避免迁移授予新菜单后旧前端短暂收到无法解析的 view；执行新增表、索引、权限、role ID 1 授权及关联 principal version 递增的版本化迁移；
3. 部署包含 redeemcode、wallet 事务参与接口和 Redis limiter 的后端；每个新实例必须先通过启动时 principal reconciliation，未通过的实例不得接收流量；
4. 切走仍运行旧路由契约的实例，发布管理页、钱包入口、资金来源字典与 i18n，再恢复 Admin 流量；
5. 验证 role ID 1 的 active Admin 用户可以访问新管理路由，其他未授权角色被拒绝；
6. 用测试码完成一次生成、兑换、资金明细与本人重放 smoke。

迁移不能放进应用启动。已经发生兑换后若应用回滚，只能暂时隐藏新入口；兑换码表、钱包流水、余额和累计充值事实必须保留，不能删除或逆向扣回。

## 15. 后续 money units 迁移

AI 计费项目实施时，将本设计纳入同一维护窗口：

```text
redeem_code_batches.amount_units
  = amount_cents * 1_000_000
```

迁移必须在修改数据前校验所有 `amount_cents` 非负且不超过 `floor(MaxInt64 / 1_000_000)`，逐批验证精确相等后删除旧 cents 字段。旧版兑换 API、支付 writer 和钱包 writer 必须全部停止，禁止 cents/units 双写或新旧版本同时兑换。

兑换记录不需要重算钱包：既有 `wallet_transactions` 会随整个钱包账本统一迁移；`source_type=redeem_code` 与 code ID 保持不变。

## 16. 可观测性

至少记录：

- 生成批次数量、码数量和失败原因；
- unused、used、voided、expired 数量；
- 兑换成功、本人幂等重放、通用不可用、限流和依赖故障数量；
- 从兑换请求到钱包事务提交的延迟；
- 作废与兑换竞态冲突；
- 钱包来源唯一冲突和溢出拒绝；
- 管理员生成、导出和作废审计事件。

所有原因使用受控枚举。受控关联日志字段只能记录用户 ID、兑换码 ID、批次 ID 和钱包流水 ID；完整码在任何日志字段中都禁止记录。

## 17. 针对性测试

Codex 实施时只自动运行预计单条两分钟内完成的针对性检查：

- 随机码格式、字符集、规范化、内存去重和数据库唯一冲突重试；
- 金额字符串、两位小数、上下界、数量、过期时间和请求指纹校验；
- 管理端生成请求响应丢失后的幂等重放，包括首次创建使用已过期时间会拒绝、原批次过期后同 request ID/同指纹仍返回原批次；
- unused、expired、voided、used 状态及作废幂等；
- 并发兑换只有一个用户获胜，同一用户重放不重复入账；
- 兑换与作废竞态只有一个终态；
- 码状态、余额、累计充值和钱包流水同事务回滚；
- 钱包加法溢出在写入前拒绝；
- `redeem_code + code_id` 资金来源唯一；
- 失败限流 10 分钟/10 次、第 10 次与后续 429 边界、阈值优先于本人重放、客户端取消后仍计数、429 `Retry-After`、无永久 per-user key 和 Redis fail closed；
- 普通用户错误不泄露未知/过期/作废/他人已使用差异；
- 管理路由权限、role ID 1 授权、自助接口 `Authenticated()` 与所有权边界；
- role ID 1 授权后关联用户 principal version 递增，旧 route-access cache 不能继续拒绝新权限；
- 完整码响应 `no-store`，且完整码不进入 URL、持久化前端 store、日志、审计或数据库驱动错误；
- 管理页生成/作废/有界导出和“我的钱包”兑换刷新；
- 资金明细展示与筛选“兑换码充值”；
- Admin Contract Bundle 漂移、迁移校验和 `git diff --check`。

不由 Codex 自动运行 `go test ./...`、全仓 race、完整前端 build/coverage、Docker 构建、全量 Playwright 或其他预计超过两分钟的脚本；这些命令只在交付说明中列给用户决定是否手动执行。

## 18. 验收标准

1. 管理员可一次生成 1 至 1000 个同面额安全随机码，并可设置永久或明确过期时间。
2. 生成响应丢失后用同一 request ID 重试不会发行第二批码。
3. 管理员可在支付管理下查看、复制、筛选、按不超过 10000 行的结果导出并作废未使用码；更大导出必须先缩小筛选范围。
4. 已使用码不可修改、作废、删除或重新启用；全部历史继续可审计。
5. 普通登录用户可在“我的钱包”兑换，未获得后台码库读取权限。
6. 成功兑换原子增加余额和累计充值，并恰好写一条“兑换码充值”资金流水。
7. 并发用户争抢同一码时最多一个用户入账；未被失败限流阻断的本人重放返回原兑换事实且不重复入账。
8. 未知、过期、作废和他人已使用对普通用户返回同一不可用错误。
9. 同一用户第 10 次失败写入后，后续请求在 10 分钟固定窗口到期前被限流；主动取消请求不能逃避已分类失败的计数，Redis 不可用时不能继续试码。
10. 管理页面和三个操作权限明确授予 `roles.id=1`，其他角色不自动获得权限。
11. 兑换码不创建支付订单、不触发支付回调，也不新增第二套余额事实。
12. 明文码不会进入日志、指标、trace、错误响应或操作审计 payload。
13. 本期金额全程使用整数 cents；后续可在维护窗口精确迁移为 money units。
14. 实施只自动执行短而针对性的测试，长脚本交由用户手动决定。
