# 可扩展平台内核与 P09 遗留平台退役设计

**日期：** 2026-07-20

**状态：** 已确认设计，等待书面复核

**适用范围：** `admin_back_go`、`admin_front_ts`、P09 Task 2/4/6/7/8/9

## 1. 背景与纠正

P09 原计划把“当前只保留 Admin 产品”错误地实现成“架构永久只允许
Admin”：删除认证平台新增、删除和启停接口，去除权限与角色的平台维度，
把会话、登录日志和通知收缩到 Admin，并准备给数据库平台字段增加
`platform = 'admin'` 约束。

这与已确认的产品路线冲突。当前阶段只运行 Admin，但 P09 完成后的下一阶段
会接入新的独立平台。新平台需要自己的认证策略、权限树、会话、登录日志和
通知受众。`auth_platforms` 及其关联的平台隔离能力是平台内核，不是 App 或
Canvas 的遗留实现。

本设计纠正 P09 的边界：

> P09 删除既有 App/Canvas 产品实现与遗留数据，但保留并验证可扩展的平台
> 内核。当前运行平台只有 Admin，不代表平台模型永久退化为单例。

## 2. 目标

1. 物理删除 App/Canvas 的 transport、route、menu、运行时代码和已分类数据。
2. 保留完整的认证平台管理、平台策略和跨模块平台隔离能力。
3. 当前只让编译期注册的 Admin 适配器处理请求。
4. 未注册平台即使存在数据库配置，也不能通过 Admin 路由获得运行能力。
5. 未来接入新平台时不需要恢复已删除的 App/Canvas 代码，也不需要拆除
   `admin-only` 数据库约束。
6. 继续遵守“正式后端文档是前端唯一接口契约”；Task 7 发布正式 Bundle
   之前，前端不得预先猜测新契约。

## 3. 非目标

- P09 不实现任何尚未提供的新平台项目。
- P09 不接受任意客户端请求头作为可信平台来源。
- P09 不允许仅向 `auth_platforms` 插入一行数据就自动生成路由或开放登录。
- P09 不保留 App/Canvas 的兼容别名、隐藏路由、运行时 mock 或字段兜底。
- P09 不通过 GitHub Workflow、Tauri 或桌面发布单元部署。
- P09 不在缺少新平台正式契约时推测其字段、登录方式或权限关系。

## 4. 核心术语

### 4.1 平台配置

`auth_platforms` 中的记录。它保存平台代码、名称、登录方式、验证码策略、
token TTL、会话绑定和注册策略。平台配置描述安全策略，不代表代码已经拥有
该平台的 transport。

### 4.2 平台适配器

后端源码中显式注册的一组 transport、路由、认证入口和契约。适配器负责在
可信边界内写入平台 provenance。P09 完成时只注册 Admin 适配器。

### 4.3 可运行平台

只有同时满足以下条件的平台才可处理请求：

1. 存在经过审核并编译进后端的平台适配器；
2. 适配器代码在平台注册表中显式注册；
3. `auth_platforms` 存在对应且启用的安全策略；
4. 对应路由、权限和正式 Contract Bundle 已发布。

数据库配置不能替代任何一个代码或契约条件。

### 4.4 平台 provenance

由可信 transport 内部写入并贯穿权限、会话、日志、通知和业务记录的平台
代码。provenance 不能来自未经验证的客户端 header、query 或 body。

## 5. 架构决策

### 5.1 平台内核与产品适配器分离

平台内核继续提供：

- 认证平台 CRUD、启停及策略查询；
- 平台代码格式、唯一性和状态校验；
- 权限定义与角色授权的平台维度；
- 会话、登录日志和统计的平台维度；
- 通知任务与通知受众的平台维度；
- 用户、导出和需要 provenance 的其他模块的平台边界；
- 小接口形式的平台目录/注册表依赖，避免业务模块互相导入具体实现。

产品适配器只负责某个平台的路由、请求模型和 provenance 注入。删除 App 或
Canvas 适配器不应修改平台内核的通用数据模型。

### 5.2 配置目录与运行注册表职责不同

- `auth_platforms` 是可管理的配置目录，可以为后续平台预先保存策略。
- 运行注册表是代码事实，只包含已经实现并发布的适配器。
- P09 的运行注册表只有 `admin`。
- 平台管理 API 可以创建格式合法的新代码，但该记录在适配器发布前不可路由。
- 运行时代码以“注册表允许且策略启用”为共同条件，缺少任一条件都失败关闭。

不得把数据库目录硬编码成 `[]string{"admin"}`，也不得因为目录中存在某个
代码就自动信任对应请求。

### 5.3 Admin transport 的可信来源

Admin 登录、刷新、鉴权和业务路由内部固定使用 `admin` provenance。客户端
提供 `platform: app`、`platform: canvas` 或任意未来代码时，不能改变 Admin
transport 的平台身份。

未来平台必须拥有自己的适配器；其 transport 同样在服务调用前内部写入已
注册代码。共享认证 service 可以接收可信 transport 传入的平台代码，但不
直接解析不可信客户端平台标识。

### 5.4 跨模块隔离

以下数据和操作继续保留平台键：

- 权限定义、角色权限树和权限缓存；
- access/refresh session、单会话指针、撤销和统计；
- 登录日志、登录失败记录和筛选；
- 通知任务、通知记录、实时受众和领取任务；
- 用户 provenance、导出任务及其他正式文档定义的平台字段；
- 通用 AI run/task 中正式存在的平台 provenance。

读取、写入、更新、删除、缓存失效和统计都必须使用明确的平台键。测试必须
使用不同的平台值证明没有串用，不能只用数值或字符串恰好相同的样例。

`all` 仅可作为通知系统已正式定义的虚拟受众，不是可登录平台。它不能进入
会话、权限或登录日志的平台集合。广播时只能展开到已注册且策略允许的目标，
不能把未知数据库值当作运行平台。

## 6. 认证平台管理契约

P09 必须保留以下 Admin 管理接口及其正式权限/审计策略：

- `GET /api/admin/v1/auth-platforms/page-init`
- `GET /api/admin/v1/auth-platforms`
- `POST /api/admin/v1/auth-platforms`
- `PUT /api/admin/v1/auth-platforms/:id`
- `PATCH /api/admin/v1/auth-platforms/:id/status`
- `DELETE /api/admin/v1/auth-platforms/:id`
- `DELETE /api/admin/v1/auth-platforms`

现有保护继续成立：

- `admin` 不允许删除；
- `admin` 不允许禁用；
- 平台代码创建后不可通过普通编辑静默改名；
- 重复或格式非法的平台代码明确报错；
- 必填安全策略缺失属于 `missing/error`，不得生成默认业务配置；
- 真实响应不符合正式契约时直接暴露契约问题，不做字段兼容。

## 7. 权限、角色、会话、日志与通知

### 7.1 权限与角色

- 权限定义继续保存明确 `platform`。
- 创建、更新、列表和初始化契约继续表达平台选择。
- 角色页继续按平台展示并分配独立权限树。
- 权限缓存和 principal version 必须按平台隔离。
- 当前数据清理后只存在 Admin 权限，不代表接口字段被删除。

### 7.2 会话与登录日志

- 管理查询继续支持正式契约定义的平台筛选和分布统计。
- 新会话的平台值来自适配器，不来自客户端自报。
- P09 删除已分类的 App/Canvas 会话和登录记录，但不删除通用查询能力。
- 新平台上线后能直接拥有独立 TTL、单会话策略、撤销范围和审计记录。

### 7.3 通知受众

- 通知任务继续支持明确平台受众和正式定义的 `all` 虚拟受众。
- 创建、领取、取消、删除、统计和实时投递都按受众隔离。
- P09 删除 App/Canvas-only 数据，并按已批准的数据规则处理旧 `all` 数据；
  不把运行时代码永久固定为 Admin。
- 新平台未注册时不能成为实际投递目标。

## 8. 数据库收口

Task 6 仍需恢复证明和新的破坏性授权，但迁移目标调整为：

### 删除

- 已分类的 App/Canvas sessions、login logs、permissions、role grants、
  notifications、exports 和产品 AI 数据；
- `app`、`canvas` 对应的 `auth_platforms` 记录；
- 空的 `canvas_video_tasks` 兼容表；
- 经 P08R 冻结且在新授权后允许删除的 `client_versions`；
- 已证明无运行时读写者的历史兼容列。

### 保留

- `auth_platforms` 表、索引、唯一约束和通用策略列；
- 各核心表的 `platform` 列及其查询索引；
- 平台相关 repository/service/contract 能力；
- Admin 数据和未来平台所需的通用 schema。

### 约束

- 不添加 `auth_platforms.code = 'admin'` 约束；
- 不给通用 provenance 列添加 `platform = 'admin'` 约束；
- 可以永久拒绝已经退役的保留代码 `app`、`canvas`；
- 可以约束平台代码格式、状态及正式数据不变量；
- 不允许通过猜测把未知旧数据改写成 Admin；
- destructive DDL 前仍必须重新取得用户明确批准。

最终 invariant 证明“当前只存在 Admin 活跃产品数据”和“schema 仍可承载正式
注册的新平台”同时成立。

## 9. Contract Bundle 与前端

Task 7 后端 Bundle 必须保留：

- 认证平台完整管理 operations；
- 权限、角色、会话、登录日志和通知的正式平台字段；
- 平台隔离所需的请求/响应 schema；
- 每条路由唯一的 permission/audit decision。

Task 2 只能在该 Bundle 发布后同步。前端删除 App/Canvas 字面量、页面分支和
旧菜单，不删除认证平台页面或通用平台选择能力。生成类型必须来自后端
Bundle，不保留手写备用字段、旧字段兼容或运行时 mock。

## 10. 新平台接入流程

未来每个新平台按以下顺序进入：

1. 用户提供项目与正式需求；
2. 确认平台代码、transport、认证方式和契约；
3. 实现并注册独立平台适配器；
4. 发布匹配的后端正式 Contract Bundle；
5. 创建或启用 `auth_platforms` 策略；
6. 配置该平台独立权限树、角色和通知受众；
7. 通过平台隔离、会话、日志、通知和 Docker 验收；
8. 才允许生产流量进入。

新增平台不复用 Admin transport 冒充 provenance，也不恢复 App/Canvas 兼容
代码。

## 11. 测试与永久防线

P09 必须新增或保留以下证明：

1. 认证平台七个管理 operation 全部存在且权限/审计正确；
2. Admin 无法删除或禁用；
3. 新平台配置记录不会让 Admin header/platform 参数改变身份；
4. 未注册平台即使策略启用也没有可调用 transport；
5. 两个平台使用不同代码时，权限树、缓存、会话、日志和通知互不串用；
6. `app`、`canvas` transport、route、menu 和生成契约完全不存在；
7. 数据库不存在 App/Canvas 活跃数据，但通用 platform schema 仍存在；
8. 必要平台字段缺失明确失败，不回退 Admin；
9. 前端只消费 Task 7 Bundle，不猜测字段；
10. 最终完整 Docker gate、回滚演练和人工功能验收通过。

架构 guard 应同时拒绝两类回归：遗留 App/Canvas 复活，以及平台内核被再次
误删或锁死成永久单例。

## 12. P09 任务调整

- **Task 4：** 从“后端永久收缩为 Admin”改为“清除遗留产品值并保护平台
  内核”。恢复认证平台 CRUD、权限/角色平台维度、会话/日志平台维度和通知
  受众；只让当前 Admin adapter 可运行。
- **Task 5：** 删除 Canvas 术语但保留通用 AI capability 的平台 provenance。
- **Task 6：** 删除遗留行和明确的兼容 schema，不添加 Admin-only 平台约束；
  destructive 阶段继续设置新授权停点。
- **Task 7：** 发布保留平台内核的正式 Bundle，再同步前端 Task 2。
- **Task 8–9：** Docker-only 发布与证明同时验证“当前单 Admin”和“平台内核
  可扩展”两个不变量。

## 13. 验收标准

设计完成的判定不是“代码中只剩字符串 admin”，而是：

- 当前只有 Admin 产品适配器、路由和活跃数据；
- App/Canvas 的产品实现与数据已按证据退役；
- 认证平台管理和所有平台隔离核心仍完整；
- 未注册平台严格失败关闭；
- 接入新平台无需恢复旧代码或拆除单例数据库约束；
- 正式契约、前后端生成物、数据库 schema、Docker 发布和回滚证明一致。
